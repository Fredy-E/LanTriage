# LanTriage supported formats — exact subset, validation and uncertainty

This document states **exactly** what LanTriage parses, what it refuses, what it
counts as *not decoded*, and which primary specification each rule comes from.
Nothing here is a network-health claim: the analyzer reports what a capture
file contains and marks everything it could not use.

All fixtures used to test these rules are **self-authored synthetic byte
sequences** (`fixtures/`, generated by `tests/fixtures.cjs`). They are not
captures of real hardware or real traffic.

## 1. Container formats

### 1.1 Classic pcap (supported)

Sources: `pcap-savefile(5)` (libpcap savefile format, tcpdump.org man page,
21 Jan 2025) and `draft-gharris-opsawg-pcap-01` (PCAP Capture File Format,
December 2020, §4 "File Header").

| Element | Rule implemented |
|---|---|
| Magic | `0xa1b2c3d4` (µs) and `0xa1b23c4d` (ns), in both byte orders → 4 accepted variants. The pre-2.4 "modified" magic `0xa1b2cd34` is **explicitly rejected** (`E_MAGIC`) rather than guessed at. |
| File header | 24 octets; shorter input → `E_HEADER_TRUNCATED`. Major version must be 2 → else `E_VERSION`. |
| SnapLen | Must not be zero (`E_SNAPLEN`); records longer than SnapLen are delivered at most SnapLen bytes with a visible `W_SNAPLEN_CAP` and limited coverage (fix round 2: truncated:true, counts.truncated+1; the man page: "when libpcap is reading from a savefile, it delivers at most N bytes"). |
| LinkType field | 16-bit link type in the low bits; Reserved3/R/P/FCS-len bits per the man page layout. Non-zero reserved bits produce `W_LINKTYPE_BITS`; the FCS fields are recorded but FCS bytes are **not** validated or stripped. |
| Per-packet header | 16 octets (ts_sec, ts_frac, incl_len, orig_len); a file ending inside a record header/data stops parsing with `W_FILE_TRUNCATED` and limited coverage. |
| Lengths | `incl_len > orig_len` → record rejected (`W_RECORD_LENGTHS`); `incl_len` beyond the end of file → rejected (`W_FILE_TRUNCATED`). |
| Timestamps | `ts_frac ≥ 10^6` (µs file) or `≥ 10^9` (ns file) is **invalid** and displayed as invalid (`W_TIMESTAMP_FRACTION`); never silently reformatted into a confident time. |

Only LINKTYPE 1 (Ethernet) is decoded. Any other link type is counted as
*not decoded* (`linktype-unsupported`).

### 1.2 pcapng (supported subset)

Source: `draft-tuexen-opsawg-pcapng-05` (PCAP Next Generation Capture File
Format, July 2022).

| Block | Support |
|---|---|
| Section Header Block (0x0A0D0D0A) | Fully parsed: byte-order magic must be `0x1A2B3C4D` (`E_BOM` otherwise); major must be 1; minor 2 is treated as 0 (draft §4.1); section length `-1` = unspecified, otherwise it is checked against the consumed blocks (`W_SECTION_LENGTH`). Its option area is structurally framed and counted; no SHB option is interpreted. |
| Interface Description Block (type 1) | Parsed: link type, snaplen, and options `if_name` (2), `if_tsresol` (9), `if_tsoffset` (14). The **declared** `if_tsresol` base/exponent (0..127) is recorded exactly as declared and is never replaced by another scale; resolutions finer than the exact display range are converted to milliseconds and clearly marked approximate (`W_TSRESOL`). Option length mismatches warn (`W_OPTION_LENGTH`) and are counted as malformed. Other option codes are counted and warned by code only (`W_OPTION_UNSUPPORTED`); their content is never interpreted or exported. |
| Enhanced Packet Block (type 6) | Parsed: interface id (must reference an IDB in the **same section** — draft §4.3); timestamp as **two 32-bit fields — Timestamp (High) at block offset 12, then Timestamp (Low) at block offset 16, each read in the section's byte order** (draft §4.3 Figure 11; Wireshark `wiretap/pcapng.c` combines the two fields at lines 2209-2210; libpcap `sf-pcapng.c` at lines 1149-1156), value = High·2³² + Low; captured/original lengths (captured > original → rejected), padding excluded from the captured length; a captured length beyond the interface snaplen is delivered capped with W_SNAPLEN_CAP and limited coverage (fix round 2: truncated:true); the option area after the padded packet data is structurally framed and counted (no EPB option is interpreted). |
| Simple Packet Block (type 3) | Parsed: belongs to the first interface of its section (draft §4.4); a section with more than one interface rejects it visibly (`W_SPB_INTERFACE`); an original length beyond snaplen is delivered capped with W_SNAPLEN_CAP and limited coverage (fix round 2: truncated:true); no timestamp — displayed as "no timestamp (Simple Packet Block)". |
| Everything else (Packet Block, Name Resolution, Interface Statistics, Decryption Secrets, custom/unknown blocks) | Skipped **by declared length** and counted (`unsupportedBlocks`) with a coverage reason. |
| Block framing | Total length must be a multiple of 4 and consistent with the trailer (`W_BLOCK_LENGTH`, `W_BLOCK_TRAILER` stop parsing with limited coverage); a file that starts with a known block type but no SHB is reported as `E_NO_SHB`. |

**Option framing (all supported blocks).** SHB, IDB and EPB option areas are parsed as bounded
structures: each option's declared length must fit the remaining area (overrun →
`W_OPTION_LENGTH`), a code-0 end-of-options marker must declare length 0 (otherwise
`W_OPTION_END_MARKER`), and the option's padding must fit (`W_OPTION_PADDING`). Options this
subset does not interpret are counted (`unsupportedOptions`) and warned with their numeric code
and byte offset only (`W_OPTION_UNSUPPORTED`) — a benign end-of-options marker is **not**
"unsupported". Malformed option framing is counted (`malformedOptions`). Both counters are
visible in the viewer summary and in both report formats. Raw option bytes and option text are
never stored, rendered or exported.

**Correction (fix round 1, 2026-10-11).** An earlier revision of this document claimed the EPB
timestamp was "a single 64-bit integer in section byte order" (low word first in little-endian
files). That claim was wrong and is retracted: the normative layout is two separate 32-bit
fields — Timestamp (High) at block offset 12, then Timestamp (Low) at block offset 16 — **each
read in the section's byte order**, combined as High·2³² + Low. That is what the draft's
Figure 11 draws and what both Wireshark and libpcap implement. Defect history and the primary
citations re-verified for this correction: `verification.md` §2.

Multiple sections are supported; **interface ids are per section** and are never
merged across sections. Sections may differ in byte order (mixed-endian files
parse; the summary shows the first section's order and every section's own
order is used for its fields).

### 1.3 Timestamps

* pcap: seconds + µs or ns, printed with 6 or 9 fraction digits, marked exact.
* pcapng: the declared `if_tsresol` (base 10 or base 2, exponent 0..127) is recorded per
  interface exactly as declared and is **never replaced**; 10^-n with n ≤ 9 → exact with n
  digits; binary resolutions or decimal n > 9 → converted to milliseconds and **marked
  approximate** (`~… (approx, 2^-n s units)`), with the declared resolution stated in the text.
  `if_tsoffset` (signed 64-bit seconds) is applied per interface.
* Precision (fix round 2): the EPB raw tick count (unsigned 64-bit) and the signed
  `if_tsoffset` are kept as `BigInt` through the resolution-aware quotient/remainder
  conversion. A large raw tick count is **not** pre-rejected at 2^53: when the quotient
  and remainder scale down (or cancel with a large negative offset) into an exact
  displayable time, the exact display is returned (e.g. modern nanosecond ticks above
  2^53, the full uint64 nanosecond range when its seconds fit, and `9007199254740993`
  ticks cancelled by `−9007199254740993` s to exactly `1970-01-01 00:00:00 UTC`). Only a
  final result whose seconds fall outside the exact 53-bit integer range or outside the
  displayable `Date` range is reported as `timestamp out of displayable range` with
  `seconds:null`/`exact:false` and `W_TIMESTAMP_RANGE` — a rounded numeric seconds value
  is never exported as exact. `if_tsoffset` values outside the safe integer range are
  stored as exact decimal strings (JSON-safe; `String()` matches the original) so large
  offsets never become silently rounded numbers.

## 2. Frame and protocol subset

### 2.1 Ethernet (LINKTYPE 1)

Ethernet II only. `ethertype ≤ 1500` is an 802.3 length field → LLC/SNAP frames
are *not decoded* (`llc`). IPv6 (`0x86DD`) and any other ethertype are counted
as *not decoded* (`ipv6`, `non-ip`).

### 2.2 VLAN (bounded)

802.1Q (`0x8100`), 802.1ad (`0x88A8`) and `0x9100` tags are unwrapped up to
**two** tags; the VLAN ids are attached to the packet and to every evidence
reference. A third tag is *not decoded* (`vlan-nested`).

### 2.3 ARP

Source: RFC 826 (Packet format: ar$hrd, ar$pro, ar$hln, ar$pln, ar$op, ar$sha,
ar$spa, ar$tha, ar$tpa; op 1 = request, 2 = reply).

Decoded only for `hrd=1` (Ethernet), `pro=0x0800` (IPv4), `hln=6`, `pln=4`;
anything else is *not decoded* (`arp-variant`) and never mis-sized. Op 3/4
(RARP) is *not decoded* (`rarp`). Observations distinguish request, reply,
**probe** (sender protocol address 0.0.0.0) and **announcement** (gratuitous:
sender == target protocol address, op 2).

### 2.4 IPv4 / UDP

IPv4 only; header options are skipped by IHL (not decoded, not interpreted).
Fragments (MF flag or non-zero fragment offset) are *not decoded*
(`fragmented`) — a fragment is never reassembled and never decoded as DHCP.
`total length` beyond captured bytes → *not decoded* (`truncated-payload`,
`W_IP_LENGTH`); trailing bytes beyond the total length (Ethernet padding) are
ignored. UDP length must be ≥ 8 and fit the captured bytes (`W_UDP_LENGTH`);
bytes beyond the UDP length are padding and ignored. IP and UDP checksums are
**not verified** (documented limitation).

### 2.5 DHCP (UDP 67/68)

Source: RFC 2131 §2–3 (message format, Table 1 fields) and RFC 2132
(option codes: 12 host name §3.14, 50 requested IP §9.1, 51 lease §9.2,
52 overload §9.3, 53 message type §9.6, 54 server id §9.7, 55 parameter request
list §9.8, 61 client identifier).

* 236-octet BOOTP header + magic cookie `0x63825363`; a missing cookie is
  flagged (`dhcp-no-cookie`) and options are not parsed, but header fields
  (op, xid, chaddr, addresses) are still reported.
* Message types 1–8 are named (DISCOVER/OFFER/REQUEST/DECLINE/ACK/NAK/RELEASE/INFORM);
  unknown values warn (`W_DHCP_MSG_TYPE`).
* Option lengths are validated against the remaining bytes; an overrun stops
  option parsing and marks the packet `dhcp-option-overrun` (`W_DHCP_OPTION_LEN`)
  — the decoded prefix is kept, the rest is **not** presented as healthy.
* Option overload (52) is **declared unsupported** (`W_DHCP_OVERLOAD`): the
  sname/file option space is not parsed.
* Client hardware address uses `chaddr` with `hlen=6` (Ethernet); other `hlen`
  values are summarised, not decoded as a MAC.

### 2.6 mDNS (UDP 5353)

Sources: RFC 6762 (port 5353 §5.2/§5.3; QU bit = top bit of the class field in
questions §5.4; cache-flush bit in response class fields §10.2; ID zero for
multicast responses §18.1; TTL 120 s for address records / 75 min otherwise §10)
and RFC 1035 §4.1 (message format) and §4.1.4 (name compression).

* Questions: name, type (A/AAAA/PTR/SRV/TXT/ANY named), QU bit.
* Answers/authority/additional records: name, type, cache-flush bit, TTL;
  RDATA decoded for A (IPv4), AAAA (expanded hex groups), PTR/CNAME/NS (name),
  SRV (priority/weight/port/target), TXT (bounded strings). Unknown RDATA keeps
  only the type and length — **raw RDATA is never stored or exported**.
* Compression pointers: two-octet `11xxxxxx` form with a 14-bit offset from the
  message start (RFC 1035 §4.1.4). The parser enforces: offset inside the
  message (`dns-pointer-range`), pointer must reference a **prior** occurrence,
  no revisit and at most 64 hops (`dns-loop`), label ≤ 63 octets
  (`dns-label-length`), name ≤ 255 octets (`dns-name-length`), records bounded
  per message (`W_LIMIT_ANSWERS`).
* A name that cannot be decoded stops that message with a visible warning; the
  packet is never reported as decoded-clean.

## 3. Hard limits (all visible when hit)

| Limit | Value | Behaviour when exceeded |
|---|---|---|
| `maxBytes` | 32 MiB | Hard error `E_TOO_LARGE` (nothing parsed) |
| `maxPackets` | 20 000 | Parsing stops, `W_LIMIT_PACKETS`, coverage limited |
| `maxBlocks` | 50 000 | Parsing stops, `W_LIMIT_BLOCKS` |
| `maxObservations` | 2 000 | Analysis stops adding, `W_LIMIT_OBSERVATIONS` |
| `maxWarnings` | 200 | Routine warnings suppressed after a visible `W_LIMIT_WARNINGS` marker; `W_LIMIT_*` warnings take priority over routine ones |
| `maxStringBytes` | 255 | Stored strings truncated with a `…` marker |
| `maxRefsPerItem` | 8 | Evidence refs per finding truncated (visible in the ref list) |
| `maxDnsJumps` / `maxAnswersPerMessage` | 64 / 64 | Name resolution fails / records stop with `W_LIMIT_ANSWERS` |
| `maxVlanTags` | 2 | Deeper nesting is *not decoded* |
| `maxSections` / `maxInterfacesPerSection` | 64 / 256 | Parsing stops / interfaces ignored with visible warnings |

## 4. Findings and their uncertainty

Findings are computed **per context** = (pcapng section, interface id, VLAN id
list). Claims are never merged across contexts, which is the counterexample the
suite exercises (same IP on two MACs in different VLANs, and in different
sections, produces no finding).

| Finding | Trigger | Explicit counterexamples carried by the finding |
|---|---|---|
| `possible-ip-mac-conflict` | One IPv4 address claimed by ≥ 2 hardware addresses via non-probe ARP within one context | probes excluded; VLAN/section/interface separation; virtual-router/failover MACs; adapter change or MAC randomisation |
| `probe-for-in-use-address` | ARP probe (sender 0.0.0.0) for an address observed in use (ARP claim or DHCP offer/ACK) in the same context | probing is normal startup behaviour; probes never count as claims; capture timing may differ |
| `possible-duplicate-dhcp-assignment` | Same `yiaddr` offered/ACKed to ≥ 2 different client hardware addresses in one context | same-client retransmissions are not duplicates; separate contexts; DECLINE/RELEASE may be missing |
| `arp-address-transition` (informational) | One hardware address seen with ≥ 2 addresses over time | reported for context only; never a conflict; order follows capture order |

The reports always carry the capture-visibility limitations (capture point
blindness, switched/VLAN invisibility, "cannot prove the absence of a problem").

## 5. Explicitly outside the subset

IPv6 (including mDNS over IPv6), TCP and any non-UDP IP protocol, IP
fragmentation/reassembly, more than two VLAN tags, LLC/SNAP, non-Ethernet link
types, RARP, non-Ethernet/IPv4 ARP variants, DHCP option-overload space, DNS
over TCP, DNS known-answer-suppression semantics, IP/UDP checksum verification,
FCS validation, encrypted/compressed payloads, and any live capture capability.
Every one of these is counted and visible; none of them can make a capture look
"clean".
